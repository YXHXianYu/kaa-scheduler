# 学园偶像大师日常自动化需求记录

更新日期：2026-06-03

## 目标

通过脚本在 Windows 上自动完成以下编排流程：

1. 定时启动 UU 加速器并确保目标游戏处于加速状态。
2. 启动 kaa，并让 kaa 按当前启用的配置执行日常任务。
3. 等待 kaa 执行完成。
4. 停止 UU 对学园偶像大师的加速。

说明：

- 学偶本体的启动与关闭由 kaa 负责，不需要单独控制游戏客户端。
- 第一版重点是稳定完成 UU + kaa 的调度和收尾。
- 当前文档同时承担需求记录和上下文防遗忘用途，后续 Q&A 应持续回填到本文件。

## 已确认需求

### 运行与调度

- 操作系统：Windows。
- 运行方式：每天 05:00 定时启动。
- 补偿策略：如果错过执行时间，则忽略，不补跑。
- 额外入口：需要保留手动一键启动能力。
- 运行占用：允许前台独占，不要求在用户正常使用电脑时无感后台执行。
- 权限：自动化脚本可以提升为管理员运行。

### 技术方向

- 第一版实现形态：Python 脚本 + Windows 任务计划程序。
- UU 部分优先考虑 GUI 自动化，必要时结合模板匹配，暂不默认依赖 OCR。
- kaa 部分优先考虑直接启动程序和进程监控，第一版不考虑配置覆盖。

### kaa 相关

- 可执行文件路径：`D:\Programs\kaa-bootstrap-0.5.1\kaa.exe`
- 推荐工作目录：`D:\Programs\kaa-bootstrap-0.5.1`
- 当前使用方式：直接运行 `kaa.exe`
- 任务触发方式：加载当前默认启用的配置即可。
- 配置来源：`D:\Programs\kaa-bootstrap-0.5.1\config.json`
- 当前决定：第一版先不考虑覆盖 `config.json`。
- 结束判定：kaa 进程退出即可视为任务完成。
- 失败处理：如果 kaa 启动或执行异常，可先用 20 分钟作为超时阈值。
- 超时策略：第一版选择保留现场，不做自动清理。
- kaa 仓库：`https://github.com/XcantloadX/kotones-auto-assistant`
- README 已确认：
  - `kaa` 命令可启动 GUI。
  - `config.json` 会在工作目录下生成和读取，因此固定工作目录是硬约束。
  - 路线图中“命令行接口”已标记完成，但 README 未给出明确 CLI 用法。
- 因此当前结论是：
  - 第一版不把 kaa CLI 视为已知稳定接口。
  - 第一版先按“固定工作目录启动 kaa + 等待进程退出”设计。
  - 如果后续确认 CLI 可稳定直接启动预设任务，再替换掉 kaa GUI 相关控制。
- 用户已确认：启动 `kaa.exe` 后会自动执行当前默认启用配置。

### UU 相关

- 启动器路径：`C:\Program Files (x86)\Netease\UU\uu_launcher.exe`
- 进程名：`uu.exe`
- 任务管理器显示名：`UU加速器`
- 主窗口实际标题：`UU加速器`
- 预期流程：
  1. 启动 UU（如果已启动则跳过）。
  2. 检测当前是否正在加速学园偶像大师。
  3. 如果已经在加速学园偶像大师，则直接复用当前状态。
  4. 如果正在加速其他游戏，则先停止当前加速。
  5. 搜索“学园偶像大师”。
  6. 点击对应搜索结果并开始加速。
  7. 等 kaa 完成后，点击“停止加速”，但保留 UU 主程序继续打开。
- 当前已知较稳定的自动化锚点：
  - 窗口标题/进程名
  - 搜索框
  - “开始加速”/“停止加速”按钮文字
- 截图已确认的界面事实：
  - 加速前主页右上角存在搜索框，可作为进入搜索流程的入口。
  - 点击搜索框后会进入一个新的子页面，相关截图待后续补充。
  - 加速中页面左侧有明显的“停止加速”按钮，可作为高置信度收尾锚点。
  - 加速中页面同时存在“启动游戏”按钮，但本项目不依赖它来启动游戏。
- 当前策略：搜索结果子页面优先尝试走 UI Automation；如果具体实现中需要图像识别目标，用户将在框架搭好后补充图片。

## 第一版建议范围

第一版只覆盖下面这条主链路：

1. 定时或手动启动自动化脚本。
2. 拉起 UU 并切到学园偶像大师加速状态。
3. 启动 kaa。
4. 等待 kaa 进程退出，或超过 20 分钟超时。
5. 正常完成时停止 UU 加速；超时时记录失败并保留现场。

不纳入第一版的复杂异常：

- UU 登录失效
- UU 更新弹窗
- 学偶登录验证失效
- 广告弹窗、网络异常、窗口被遮挡等复杂分支

这些可以在主链路稳定后再逐步补充。

## 技术路线与框架

当前建议的第一版技术路线如下：

1. 编排层
  - 使用 Python 作为唯一编排入口。
  - 同时支持手动启动和 Windows 任务计划程序定时启动。
  - 提供统一日志，记录每一步开始、成功、失败和超时。

2. UU 自动化层
  - 优先用窗口标题和进程名附着到 `UU加速器` 窗口。
  - 优先尝试使用 Windows UI 自动化能力完成聚焦、窗口激活和基础控件定位。
  - 如果控件树不可用，则退化到“窗口定位 + 模板匹配 + 键鼠输入”。
  - 第一版暂不默认引入 OCR，只有在搜索页文字和按钮无法稳定模板匹配时再补。

3. kaa 控制层
  - 以 `subprocess` 在固定工作目录下启动 `kaa.exe`。
  - 启动后直接依赖 kaa 自动执行当前默认启用配置。
  - 以 kaa 进程退出作为完成信号。
  - 以 20 分钟作为默认超时阈值。
  - 后续如确认 CLI 参数可直接启动任务，再替换为显式 CLI 调用。

4. 调度层
  - 使用 Windows 任务计划程序负责每天 05:00 触发。
  - 脚本自身保留手动运行入口。
  - 第一版不做错过执行的补偿逻辑。

5. 配置层
  - 第一版不考虑 `config.json` 覆盖。
  - 如未来确有必要，再作为增强项单独接入。

## 框架建议

如果按第一版最稳妥的方向落地，建议采用下面这套组合：

- `pywinauto`：负责附着窗口、激活窗口、读取基础控件信息
- `pyautogui`：负责兜底的点击、输入和按键操作
- `mss` 或 `Pillow`：负责截图采样
- `opencv-python`：负责模板匹配，例如定位搜索框、停止加速按钮等稳定 UI 片段
- 标准库 `subprocess` / `pathlib` / `logging` / `json`：负责 kaa 进程启动、日志和配置处理

这样组合的原因是：

- 对 UU 这类桌面应用，纯 UIA 不一定稳定，必须预留图像匹配兜底。
- 对 kaa，当前最稳定的控制手段仍然是固定工作目录下直接拉起进程，而不是先假设某个未确认的 CLI 参数存在。
- 这条路线能把 GUI 自动化范围收缩到 UU 和可能存在的一个 kaa 启动按钮，而不是把整个任务执行都压到图像识别上。
