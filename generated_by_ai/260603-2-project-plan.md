# 学偶日常调度器宏观步骤 Plan

更新日期：2026-06-03

## 文档目标

本文档给出项目的宏观实施步骤，用于后续逐步推进实现。

这份 Plan 只回答三个问题：

1. 还有哪些事情需要进一步明确
2. 项目应该按什么阶段推进
3. 每个阶段完成后，如何判断可以进入下一阶段

## 当前判断

当前已经具备进入实现阶段的条件，不需要再先做一轮泛化讨论。

当前只剩 1 个实现期确认点，需要在执行过程中逐步收敛：

1. UU 搜索结果子页面最终是否能纯靠 UI Automation 完成；如果不够稳定，再由用户在框架搭好后补充图像识别目标。

已确认事项：

- 启动 `kaa.exe` 后，会自动执行当前默认启用配置。
- 第一版先不考虑 `config.json` 覆盖。

因此推荐策略是：

- 先搭最小骨架
- 先做探针和最短主链路
- 把未确认点变成阶段内的验证任务，而不是继续停留在讨论阶段

## 项目总目标

第一版要达成的结果是：

```text
手动或定时启动脚本
  -> 脚本检查或启动 UU
  -> 脚本确保 UU 正在加速学园偶像大师
  -> 脚本启动 kaa
  -> 脚本等待 kaa 退出或超时
  -> 正常完成时停止 UU 加速
  -> 输出日志和结果
```

第一版暂不追求：

- 全异常恢复
- 自动修复登录失效
- 任何 `config.json` 覆盖能力
- OCR 作为默认基础能力

## Phase 1：搭建项目骨架

### 目标

创建最小可运行的 Python 项目结构，让后续逻辑有稳定落点。

### 本阶段要做的事

1. 创建 `app/kaa_scheduler/` 目录结构
2. 创建首批必要文件：
   - `__init__.py`
   - `__main__.py`
   - `cli.py`
   - `scheduler.py`
   - `config.py`
   - `models.py`
   - `uu.py`
   - `kaa.py`
   - `infra/logging.py`
   - `infra/process.py`
   - `infra/window.py`
   - `infra/single_instance.py`
3. 创建基础项目文件，例如 `pyproject.toml` 和基础 `README.md`
4. 建立日志目录和测试目录

### 本阶段不做的事

- 不接入真实 GUI 自动化逻辑
- 不写模板匹配
- 不写计划任务安装脚本的完整细节

### 验收标准

- `python -m kaa_scheduler --help` 或等价入口可运行
- 项目结构与框架文档一致
- 基础 import 不报错

---

## Phase 2：实现基础设施层

### 目标

完成后续所有业务都会依赖的底层通用能力。

### 本阶段要做的事

1. 在 `infra/logging.py` 中建立统一日志初始化逻辑
2. 在 `infra/process.py` 中封装：
   - 查找进程
   - 启动进程
   - 等待进程启动
   - 等待进程退出
3. 在 `infra/window.py` 中封装基础窗口能力：
   - 连接窗口
   - 激活窗口
   - 查找窗口标题
   - 发送输入和点击动作的基础接口
4. 在 `infra/single_instance.py` 中实现单实例锁

### 本阶段不做的事

- 不写业务判断，例如“当前是否加速学园偶像大师”
- 不写具体按钮定位逻辑

### 验收标准

- 进程工具可以单独被调用并返回可读结果
- 单实例锁能防止重复运行
- 日志初始化能输出到控制台和文件
- 窗口工具能成功附着或明确报错

---

## Phase 3：实现 kaa 探针与控制

### 目标

先把最确定、最简单的 kaa 进程控制链路跑通。

### 本阶段要做的事

1. 在 `kaa.py` 中实现：
   - `launch()`
   - `wait_until_finish()`
   - `is_running()`
2. 固定 kaa 的工作目录和启动路径
3. 建立超时等待逻辑，默认 20 分钟
4. 输出 kaa 进程启动日志、PID、耗时和结束结果

### 本阶段要确认的关键点

1. 已确认：启动 `kaa.exe` 后会自动开始执行当前默认启用配置。

### 验收标准

- 能稳定启动 kaa
- 能稳定等待 kaa 退出
- 超时逻辑能生效
- 不需要额外 GUI 启动动作，也能把 kaa 当作受控进程接管起来

---

## Phase 4：实现 UU 探针与基础控制

### 目标

先验证 UU 的窗口附着和基础状态控制是否可行。

### 本阶段要做的事

1. 在 `uu.py` 中实现：
   - `ensure_started()`
   - `attach_window()`
   - `get_status()`
2. 验证可否通过窗口标题 `UU加速器` 附着主窗口
3. 验证可否识别当前是否处于加速状态
4. 验证可否识别“停止加速”按钮或当前目标游戏状态

### 本阶段要确认的关键点

1. UU 搜索结果子页面的稳定锚点
2. 搜索框和开始加速动作能否通过 UI Automation 完成
3. 如果 UI Automation 不够稳定，用户将在框架搭好后补充图像识别目标

### 本阶段的决策分支

- 如果 UI Automation 足够稳定，则继续沿用
- 如果 UI Automation 不足以处理搜索页，再补模板匹配或 OCR 方案

### 验收标准

- 能稳定附着 UU 主窗口
- 能判断是否已对学园偶像大师加速
- 至少能稳定完成“停止加速”动作的验证

---

## Phase 5：打通最短主链路

### 目标

把 UU 和 kaa 串起来，形成第一条可跑通的完整链路。

### 本阶段要做的事

1. 在 `scheduler.py` 中实现主流程
2. 串联：
   - 检查或启动 UU
   - 确保目标游戏加速
   - 启动 kaa
   - 等待 kaa 退出或超时
   - 正常完成后停止 UU 加速
3. 统一汇总执行结果到 `RunResult`
4. 建立失败时的返回码和日志输出

### 本阶段不做的事

- 不做复杂异常分支恢复
- 不考虑 `config.json` 覆盖

### 验收标准

- 手动运行时可以完整跑完一次主链路
- 正常完成时能停止 UU 加速
- 超时失败时能保留现场并输出清晰日志

---

## Phase 6：补 CLI、探针模式和基础测试

### 目标

让程序具备可调试、可验证、可维护的基本工程能力。

### 本阶段要做的事

1. 在 `cli.py` 中补齐：
   - `run`
   - `probe-uu`
   - `probe-kaa`
2. 在 `models.py` 中固定运行结果结构
3. 编写最小测试：
   - `test_scheduler.py`
   - `test_uu.py`
   - `test_kaa.py`
4. 保证关键纯逻辑部分可测试

### 验收标准

- 可以独立运行探针命令
- 关键纯逻辑测试可执行
- CLI 参数行为清晰

---

## Phase 7：接入 Windows 任务计划程序

### 目标

把手动可运行脚本接到每天 05:00 的自动触发上。

### 本阶段要做的事

1. 编写 `scripts/run_manual.ps1`
2. 编写 `scripts/install_task_scheduler.ps1`
3. 固定计划任务调用入口、工作目录和日志输出位置
4. 验证计划任务运行时的路径与权限行为

### 本阶段注意点

- 计划任务只负责触发，不承载业务逻辑
- 工作目录必须稳定，否则会影响 kaa 的配置读取

### 验收标准

- 每天 05:00 能自动拉起脚本
- 手动运行和计划任务运行的行为一致
- 不会因为工作目录错误导致 kaa 找不到配置

---

## Phase 8：第二轮增强项

### 目标

在主链路稳定后，再逐步补全增强能力。

### 可能进入本阶段的内容

1. 补充搜索页模板匹配或 OCR
2. 增加失败截图
3. 增加通知能力
4. 增加更细异常分支，例如：
   - UU 更新弹窗
   - 登录失效
   - 窗口失焦

### 进入本阶段的前提

- 第一版主链路已经稳定跑通
- 失败日志足以说明当前瓶颈在哪

## 阶段执行顺序总结

推荐严格按下面顺序推进：

1. Phase 0：冻结边界与基线
2. Phase 1：搭建项目骨架
3. Phase 2：实现基础设施层
4. Phase 3：实现 kaa 探针与控制
5. Phase 4：实现 UU 探针与基础控制
6. Phase 5：打通最短主链路
7. Phase 6：补 CLI、探针模式和基础测试
8. Phase 7：接入 Windows 任务计划程序
9. Phase 8：第二轮增强项

## 近期最关键的两个执行点

如果要立刻开始实现，最近两步最关键的是：

1. 建立最小项目骨架
2. 先做 kaa 探针和 UU 探针，而不是一开始就尝试完整自动化

这是因为：

- kaa 探针能尽快确认最关键的启动行为
- UU 探针能尽快确认搜索页是否需要图像识别
- 这两件事会直接决定后续复杂度

当前没有新的阻塞问题需要先讨论。

更有效率的路径是：

- 直接按本 Plan 开工
- 在每个阶段内解决对应的不确定点
- 不在编码前继续扩展讨论范围

后续执行时，应尽量按本文档顺序推进，不要跳阶段同时铺太多面。
